The main reason is separation of responsibilities.
Controller
"How does the outside world communicate with my application?"

Deals with:
HTTP
URLs
JSON
status codes
request parameters

Service
"What should my application do?"

Deals with:
business/application logic
workflow
rules
coordination

Repository
"How do I store/retrieve data?"

Deals with:
database
queries
saving
finding
updating
deleting

So you can remember:
Controller  → HTTP
Service     → Business logic
Repository  → Data access

And in your current project:
                 Spring
                   │
        ┌──────────┴──────────┐
        ↓                     ↓
 UserController          UserService
        ↓                     ↓
     HTTP                  UserRepository
                              ↓
                         List<User>

The Controller should not know how users are stored, and the Repository should not know anything about HTTP. That's the main architectural benefit of separating these layers.
